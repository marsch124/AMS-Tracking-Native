# AMS Tracking 2.0 — written specification of the native app

Written 26 Nov 2026 for version 2.0. This file describes what is new in the native app. The rules and screens that the
native app inherits from the web app (v1.51) stay in the two files next to it and are **not repeated here**:

- `02-rules.md` — every data and logic rule (streaks, weekly targets, parts, fasting, goals, milestones, reviews, aspirations, import).
- `03-screens-web.md` — every screen of the web app, element by element, with the web's `data-testid` names.

Where this file and those two disagree, this file wins (it lists the differences explicitly).

## 1. What it is

A habit tracker with daily, weekly-target, several-part and start/stop (fasting) habits, streaks, a calendar that can be
corrected, fasting stages and rings, Stats, Last week and Last month analyses, and Aspirations. One SwiftUI app,
one target, for **iPhone, iPad and Mac** (iOS 17 / macOS 14), the same Tracking icon on all three. Data lives in one JSON
file in iCloud Drive. No server, no account, no analytics. It replaces the TestFlight "Tracking" 1.50/1.51 (a web app in a
native shell) and reuses its App Store record.

- App Store Connect app: **6839502190**, bundle id `io.github.marsch124.amstracking`, team `D24ENP83QQ`.
- Version 2.0, first build number 1 (`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` in `project.yml`).
- Project is generated by XcodeGen from `project.yml`; `tools/build.sh` runs it. Package dependency: AMS-Icons (pinned commit) for the shared icon hub.
- iCloud container `iCloud.io.github.marsch124.amstracking` (entitlements in `App/Config/AMSTracking.entitlements`, container name "Tracking" in `Info.plist`).

## 2. Layout per device

| Device | Layout |
|---|---|
| iPhone | One navigation stack. **Today** is home and has no header; it starts with the first habit card. A habit's page, Stats, Last week, Last month, Aspirations push in from the right. A **floating bar** at the bottom holds three buttons, each with its word under the mark: **Stats**, **Add** (＋), **Settings** (sliders). Add and Settings open as sheets. |
| iPad, Mac | `NavigationSplitView` in three columns: **sidebar** (Today, Stats, Last week, Last month, Aspirations, Settings, version number at the foot) · **middle column** (the chosen part, 340–520 pt wide) · **right column** (the tapped habit's page; an empty hint when none). Add and Edit are sheets. No floating bar. Content is limited to about 560 pt wide through the `Page` container. |

Sidebar marks (hand-drawn `TrackIcon`): Today = grid, Stats = chart, Last week and Last month = light bulb, Aspirations = target, Settings = sliders.

Navigation state lives in `Nav` (`RootView.swift`): `path`, `section`, `selectedHabit`, `sheet` (`addHabit`, `editHabit`, `settings`), `focusDay`, `wide`. A suggestion in Last week opens the add sheet with a `HabitPrefill` (name, icon, type, target); nothing is created until Save.

Look: Apple's standard text styles, compact rows, a habit's own colour means that habit, blue (`Ink.accent`) is for buttons and links, green/yellow/red are fasting signals, amber (`Ink.stale`) means "needs a look". Day and night both use the `Ink.*` colours. No emoji; icons are the web app's own hand-drawn strokes (`TrackIcons.swift`, drawn by `TrackIcon`).

## 3. Data

### 3.1 The file
`tracking.json` in the iCloud container's `Documents` folder (`Store.fileName`). If iCloud is not available the same file is kept in Application Support (`AMSTracking`) and Settings says "This device". The shape is the web app's backup shape (`TrackingData` in `Model.swift`), so a web backup imports here and the other way round. Added for iCloud:

- every habit and aspiration carries `mt` (last change, ms) and, once removed, `deletedAt` (ms);
- the root carries `order`/`orderMt` (shared order of habits), `format`, `savedAt`;
- fields the app does not know are kept (`extra`) and written back unchanged;
- `format` greater than the app's `currentFormat` means "this app is too old": it never writes and Settings says so.

### 3.2 Merge
`TrackingData.merged(a, b)`: record by record (habit, aspiration), the record with the newer `mt` wins; a removal (`deletedAt`) is a change like any other, so a habit removed on one device is removed everywhere. Shared settings merge by `settings.mt`; the order merges by `orderMt`. Loading always merges (never replaces) so an unsaved local change is not lost. Saving reads the file first and merges before writing (`NSFileCoordinator`, `.forMerging`). iCloud conflict copies are merged in too. All changes go through `Store.update(id){…}`, `add`, `remove`, `reorder`, `updateSettings`, … which stamp `mt`. Removed records are purged for good after 30 days.

### 3.3 Safety copies
Folder `Safety copies` beside the data (local, kept on the device). One copy named `Daily yyyy-MM-dd.json` is made by itself on the first save of each day; the last 30 daily copies are kept. **Proved:** a copy is read back, decoded, and its habit and aspiration counts compared before it counts; a failed copy is deleted. Other copies: before an import ("Copy …"), and a file the app cannot decode is parked as "Could not read …" before anything is written over it. Settings lists the copies; a copy can be looked at (`Store.peek`) and taken back.

### 3.4 Taking over the 1.51 shell app
On the first start, if this device has no habits and `Library/amsTracking.v1.json` (the safety copy written by the 1.50/1.51 web-in-a-shell app, same App Store app) exists, its habits are imported (`replaceAll`), the file is renamed `…taken-over.json`, and a bar says "Your habits from the earlier Tracking app are here". Nothing is added on a first start otherwise: there is **no sample habit** (with iCloud a new device must not add one).

### 3.5 Backup
Export backup (JSON) shares a file in the web's backup shape; Import backup asks before replacing, makes a safety copy first, and stamps every imported record so it wins over older copies on other devices. Export CSV (two files, semicolon, decimal commas) and Import fasting history are inherited (`03-screens-web.md`).

### 3.6 Removed from the web app
Update check and Update button (TestFlight brings versions); the "back up" reminder bar (daily proved safety copies replace it); the first-start sample habit; the `?fast=` links; the Cloudflare reminder server; the Capacitor shell's own safety copy and migration code.

## 4. Siri, Shortcuts, icon menu (direct)

All three change the data **directly** through `Store`/`Actions` (`applyFastAction`) — no pending queue and no waiting for the app to open. They act on the first non-archived start/stop habit.

- **App Intents** `StartFastingIntent`, `StopFastingIntent` and `AppShortcuts` phrases: "Start fasting in Tracking", "Start a fast in Tracking", "Start my fast in Tracking", "Start fasting with Tracking", "Tracking start fasting"; "Stop fasting in Tracking", "End my fast in Tracking", "Stop my fast in Tracking", "Stop fasting with Tracking", "Tracking stop fasting". Siri answers out loud without opening the app: "Fast started at 20:13. Goal 16 h, until 12:13." / "Fast ended after 16 h 5 min. Goal of 16 h met." / "You are already fasting, since 20:13." / "No fast is running." / "Open Tracking once, then try again." (no data yet). Also in Shortcuts and Spotlight; also on the Mac.
- **Home Screen icon menu** (iPhone, iPad): one entry that fits now — **Start Fasting** (moon, asset `QuickStart`) or **Stop Fasting** (fork and knife, asset `QuickStop`) with the subtitle "Since HH:MM". Refreshed after every change (`SideEffects.refresh`).
- Same message and Undo bar as tapping the card when the app is open.

## 5. Reminder and badge (per device)

Stored in `DeviceSettings` (UserDefaults of this device, **not** in the shared file). Reminder: local notifications, ids `ams.reminder.0…29`, one per day for the next 30 days at the chosen time (default 20:00), text "N still open: A, B" or "Time to fill in your tracked items"; a day with nothing open gets none; re-planned on every launch, foreground and data change. Badge: number of scheduled habits still open today (off until switched on in Settings); on the Mac it is the Dock tile. Both need notification permission. No server of any kind.

## 6. Mac specifics

Right-click a card: Done today, Skip today, Yesterday done, Start/Stop fast, Edit. ⌘N new habit. Escape = Cancel on every sheet (`.keyboardShortcut(.cancelAction)`). The window and sidebar follow the standard Mac conventions; the Dock icon shows the badge.

## 7. Screens (native additions to `03-screens-web.md`)

Every web screen exists (Today, habit page, add/edit sheet, day sheets, fast editor, Stats, Last week, Last month, Aspirations, Settings, How it works, What's new). Differences:

- **Today**: cards, grid/list layout, week dots, tap areas, swipe (right done, left skip) with a ring that is grey until far enough and green when it will fire; **reorder** by pressing and holding a card (not the round button) and dragging it onto another, a blue outline marks the target; the order is saved at once with Undo and is shared by iCloud. The Last week / Last month buttons sit under the cards on iPhone and are sidebar entries on iPad/Mac.
- **Settings** (sheet on iPhone, column on iPad/Mac): iCloud status and "Sync now", safety copies, export/import backup, CSV, fasting-history import, reorder habits (drag handles), layout, theme, daily reminder, icon number, archived habits, How it works, What's new, version. There is no "Check for app update".
- **How it works** (`GuideScreen.swift`): collapsible topics (Your devices and the screens; Daily and weekly habits; Several parts; Fasting; Siri, Shortcuts and the icon menu; Calendar, notes and the past; Last week and Last month; Stats, milestones and aspirations; Adding, editing, reordering; iCloud, safety copies and backups; Reminder and icon number) and the section **Signs in this app**: every mark and colour with its meaning and the drawn mark beside it (day marks, floating-bar words, blue drop outline, swipe ring, drag handle, pixel grid, fasting rings and calendar circles, stage colours, zone words, moon, fork and knife, sidebar marks, amber, icon number, red, blue).
- **What's new** (`WhatsNewScreen.swift`): a data array `Releases.all` of `Release(version, date, tagline, bullets)`, newest first. 2.0 is open by default; v1.51 down to v1.0 is the web app's history, copied word for word with its dates. Each release has a tappable heading (Show/Hide).

## 8. Accessibility identifiers

Rule: every control has a stable identifier named for what it is. Pages: `screen-today`, `screen-settings`, `screen-guide`, `screen-whatsnew` (and one per other screen). Today: `habit-list`, `card-<id>`, `card-name`, `check-<id>`, `part-<i>`, `weekdot-<i>`, `stat-<id>`, `note-dot`, `zone-labels`, `review-week`, `btn-add`, `settings`, `empty-today`. Shell: `sidebar-<section>`, `sidebar-version`, `detail-empty`, `app-version`, `toast`, `toast-text`, `toast-action`, `celebration`. Guide: `topic-<id>` for each topic heading, `signs` for the Signs heading. What's new: `version-<number>` for each release heading (e.g. `version-2.0`). The web app's `data-testid` names (see `03-screens-web.md`, section 12) are reused where a native control exists.

## 9. Tests

Lean (Martin's rule, 9 Nov 2026): one small data test per rule in `Tests/*Tests.swift` (XCTest, pure functions, fixed day keys, never `Store.shared`; `DayKey.now` pins "today"); one screen test per screen in `UITests/*UITests.swift`, launched with `-uiTesting -sample` (sample data, fresh temporary store, no iCloud), finding things only by identifier. `UITests/DocsUITests.swift`: Settings → How it works shows `screen-guide` and `signs`; Settings → What's new shows `screen-whatsnew` and `version-2.0`. Launch arguments: `-uiTesting`, `-sample`, `-firstStart`, `-grid`, `-needsUpdate`, `-effects`. Apple's/GitHub's run after each push is the safety net; unit tests may run on the Mac with `-only-testing:AMSTrackingTests`.

## 10. Build and release

- Build: `tools/build.sh` (xcodegen, then xcodebuild for the iPhone simulator; derived data outside `~/Documents` because of extended-attribute codesign traps).
- Release: `tools/release.sh <build> [ios|mac|both]` archives with cloud signing and uploads with the ADMIN App Store Connect key; then check Apple's verdict on the upload and run `tools/release-to-testers.py` so the build reaches the tester group (**"Martin", `c3fa83df-eb47-4dd3-97d5-1455a092a729`**) — an upload alone does not put a build in TestFlight, and the group does not pick builds up by itself.
- Same release, same round: What's new entry, How it works changes, this specification, `docs/what-to-test/<version>.txt` (at most 3,900 characters), tests.
- The old web repository's TestFlight job (the Capacitor shell) was **switched off on 26 Nov 2026**; the web app stays published as a web app and is no longer shipped to TestFlight. Version 2.0 build 1 is the first native upload; it supersedes shell build 1.51 under the same app record.
- Code lives in the GitHub repository (marsch124); commit and push with every release. No personal data in the repository.
